# Aster-Engine C++ 编码规范

版本：统一目标版 2.0

日期：2026-10-21

适用范围：引擎、编辑器、独立工具、Project SDK、项目模板及测试中的自有代码。

本文规定 Aster-Engine 一次性统一后的编码标准。文件与目录采用 `snake_case`、C++ 头文件采用 `.h`，格式采用 Allman、4 空格、120 列。其余规则根据可读性、类型安全、模块职责和长期维护确定；现有写法和迁移工作量不作为保留旧规则的理由。

“必须”表示正确性或统一标准要求；“建议”允许有具体设计理由的偏离。本文描述目标状态，不表示源码已经迁移完成。当前实现与目标的对应关系见附录。

规范覆盖全部自有代码、SDK、模板、脚本和测试。迁移作为一个完整交付完成，不设“只改新代码”“旧公开路径永久例外”或长期双命名方案。执行步骤和验收标准见第 15 节。本版文档修订本身不代表已执行代码迁移。

## 1. 项目基线与规则优先级

### 1.1 目标技术基线

| 项目 | 目标约定 |
|---|---|
| 语言 | C++20；C ABI 头文件必须同时能被 C 编译器消费 |
| 构建 | CMake 3.21+，共享入口为 `CMakePresets.json` |
| 主要开发环境 | Windows x64、Visual Studio 2022；开发机与 CI 固定并记录验证过的工具链版本 |
| 渲染 | SDL2 与 OpenGL 4.3，后端集中于现有 Render 实现 |
| 编辑器 | Dear ImGui docking；通过现有 CMake 配置获取依赖 |
| 引擎命名空间 | `tinyengine`；项目 C++ SDK 为 `tinyengine::project_sdk` |
| 项目链接入口 | `tinyengine::project_sdk`（CMake 导入目标）；项目模块不链接完整引擎 |
| 测试 | CTest、自有 C++ 测试程序及 CMake/PowerShell 集成检查 |
| 接口文档 | 中文 Doxygen，配置文件为仓库根目录 `Doxyfile` |

引擎、编辑器、工具、C++ SDK 和消费模板统一使用 C++20，通过 CMake 目标传播 `cxx_std_20`，禁用编译器语言扩展。CMake 的标准等级声明不能代替实际编译和标准库功能验证；迁移验收包含 Debug/Release 和外部 SDK 消费构建。

允许使用 `std::span` 表达借用连续区间、Concepts 表达模板约束、`std::format` 进行类型安全格式化；按接口需要使用，不为“现代化”增加抽象。C++ Modules、协程和 C++23 功能不作为默认要求；`std::expected` 不属于 C++20，不能直接作为基线 API。

语言和外部接口的硬性要求优先于外观规则；自有 C++ 接口、路径、导出名称和宏均按本文统一。涉及已分发接口或数据格式的破坏性变化，应提升版本并给出明确转换或拒绝策略，不能静默误读。第三方源码和外部协议固定名称保留；自有模板和生成器必须输出新规范。

### 1.2 设计原则

- 保持职责清晰和依赖可解释，避免为了符合通用模板而引入新架构层。
- 所有权、失效条件、线程要求和失败语义必须明确。
- 优先采用现有模块提供的能力，避免重复创建日志、路径、资源或任务基础设施。
- 性能优化需要可复现的测量；正确性检查不能因追求性能而直接移除。
- 自有接口统一命名；持久化数据和二进制接口的变化通过显式版本与转换管理。

## 2. 标识符命名

### 2.1 命名总表

| 对象 | 规则 | 示例 |
|---|---|---|
| 类、结构体、类型别名 | `PascalCase` | `ResourceManager`、`JobHandle` |
| 枚举类型、C++ 枚举值 | `PascalCase` | `ResourceState::Loading` |
| 函数、成员函数、自由函数 | `camelCase` | `loadAsync()`、`isAlive()`、`getTransform()` |
| 参数、局部变量 | `camelCase` | `assetRoot`、`deltaTimeSeconds` |
| 公共数据字段 | `camelCase` | `position`、`nearPlane` |
| 私有/受保护数据成员 | `m_` + `camelCase` | `m_resourceManager`、`m_state` |
| 具名编译期常量，包括局部 `constexpr` | `kPascalCase` | `kInvalidEntity`、`kPi`、`kMaxLights` |
| 普通运行期 `const` 变量 | `camelCase` | `fixedStep`、`frameCount` |
| 命名空间 | 全小写 `snake_case` | `tinyengine::project_sdk` |
| 模板类型参数 | `PascalCase`，短作用域可用 `T` | `TResource`、`T` |
| 模板非类型参数 | `kPascalCase` | `kCapacity` |
| 自有宏 | 模块前缀 + 大写下划线 | `TINYENGINE_BUILD_EDITOR` |
| CMake 实体目标、CTest 名称 | 小写下划线并使用项目范围前缀 | `tinyengine_material_cpu` |
| CMake 导入/别名目标 | 小写项目命名空间 + 小写下划线组件名 | `tinyengine::project_sdk` |
| 文件、目录 | `snake_case`；外部工具固定名称见第 3 节 | `resource_manager.h` |

固定宽度整数直接使用 `std::uint8_t`、`std::uint32_t` 等标准名称；移除仅缩短拼写的 `u8`、`u16`、`u32`、`u64` 别名。类型别名应表达领域含义，例如 `Entity`、`JobHandle`。C 接口使用 `<stdint.h>` 中的相应类型。

### 2.2 命名语义

- 函数使用动词或动词短语；布尔查询优先使用 `is`、`has`、`can`、`should`。
- 数据结构允许公开字段；不为 ECS 组件、序列化数据或简单数学类型机械添加访问器。
- 有验证、状态变更、缓存失效等语义时，使用明确的操作接口。
- 不使用含义不明的 `mgr`、`tmp2`、`doStuff`。循环索引、数学分量等短作用域名称可使用 `i`、`x`、`y`。
- 缩写按单词处理：类型用 `GpuBuffer`、`Aabb`、`ProjectSdk`、`PluginApi`、`SdkPaths`；函数用 `uploadGpuBuffer()`、`getSdkPaths()`；目录用 `project_sdk/`。宏中的缩写保持大写。
- 单位或空间不能从上下文判断时写入名称，例如 `rotationDegrees`、`deltaTimeSeconds`、`worldPosition`。
- 编译期常量使用 `constexpr`，不使用宏代替有类型的常量；静态编译期成员也使用 `k` 前缀，不叠加 `m_`。
- 构造、析构、运算符以及标准库定制点服从 C++ 语法和接口，例如 `ResourceManager()`、`operator==`、`begin()`。实现第三方接口时匹配其要求；自有虚接口及全部重写一并迁移。

### 2.3 C ABI 命名

`plugin_api.h`、`project_api.h` 使用可由 C 消费的声明，同时统一自有标识符：

- C 类型使用 `TinyEngine` + 模块 + 类型名，例如 `TinyEngineProjectApi`、`TinyEngineProjectResult`、`TinyEnginePluginApi`。
- 导出函数使用小驼峰和项目/模块前缀，例如 `tinyEngineProjectGetApi()`、`tinyEnginePluginGetApi()`；结构字段和回调统一为 `abiVersion`、`structSize`、`hostContext`、`getTransform`。
- 宏统一使用项目/模块前缀：`TINYENGINE_PROJECT_`、`TINYENGINE_PLUGIN_`。C 的命名常量可采用带前缀的大写宏。
- 不将 C 接口改成 C++ `enum class`、`using` 或命名空间声明。
- 导出符号改名时同步更新入口字符串、动态加载器、版本和全部消费端。字段改名本身不一定改变二进制布局，仍须检查布局、调用约定和错误语义；不能用名称相同推断 ABI 兼容。
- 序列化键属于文件格式契约，和 C++ 标识符分别管理；需要改键名时提供版本化读写和转换，不能全仓库无差别替换字符串。

## 3. 文件与目录命名

### 3.1 目标规则

1. 全部自有代码、脚本、文档文件与目录使用全小写 `snake_case`。
2. C++ 头文件使用 `.h`，源文件使用 `.cpp`；C ABI 头文件同样使用 `.h`。
3. 配对文件使用相同基础名称，例如 `resource_cache.h` 与 `resource_cache.cpp`。
4. C++ 测试文件以 `_test.cpp` 结尾；基准测试以 `_benchmark.cpp` 结尾。C 编译兼容测试保持 `.c`，例如 `project_sdk_abi_test.c`。
5. 默认把模板实现放在头文件；确需拆分时使用 `.tpp`。`.inl` 仅用于明确约定的普通内联实现。
6. 文件按职责拆分；避免 `common.cpp`、`misc.h` 等无边界的收纳文件，也不要求每个小类型独占文件。
7. 不创建仅大小写不同的两个路径。跨平台构建、`#include`、安装规则中的路径大小写必须精确匹配。

示例：

```text
resource_cache.h
resource_cache.cpp
resource_cache_test.cpp
matrix_multiply_benchmark.cpp
coding_conventions.md
platform/windows/
```

### 3.2 路径统一与必要例外

只有以下情况可以保留非 `snake_case` 名称：

- `CMakeLists.txt`、`CMakePresets.json`、`README.md`、`Doxyfile`、点号配置文件等工具和仓库入口。
- 第三方源码、外部协议或工具确实规定的名称；自有输出文件不因“由代码生成”而获得例外。
- 用户创建或导入的内容文件名允许中文、空格等受支持字符；代码命名规范不得限制用户内容。引擎随仓库交付的自有示例资产按目标规则整理，并保持 GUID 和引用正确。

旧目录与旧头文件统一改名，不保留存量豁免：`tinyengine/` 改为 `tinyengine/`，模块目录改为 `resource/`、`project_sdk/` 等，`.hpp` 改为 `.h`。自有模板文件按同一规则命名，例如 `build_info.h.in`。

目标示例为 `include/tinyengine/resource/resource_manager.h` 和 `src/resource/resource_manager.cpp`。`programs/`、`scripts/`、`intermediate/`、`saved/` 分别统一为 `programs/`、`scripts/`、`intermediate/`、`saved/`；项目生成目录也使用小写命名。

文档目录统一为 `docs/guides/`、`docs/reference/`，自有文档使用英文 `snake_case` 文件名，正文可为中文。Git 仍只管理这两类文档，迁移时同步修改忽略规则和链接；不能因目录改名把本地架构草稿、报告纳入 Git。

重命名必须一次性覆盖 include、CMake 源列表、安装/导出、模板、脚本、文档与 CI 文件匹配。源接口不保留永久旧名转发头或别名；消费端同步升级。Windows 上仅大小写改名应通过临时中间名执行两次 `git mv`，并核对 Git 最终记录。构建缓存不能靠目录改名复用，应在新路径重新配置。

## 4. 目录职责与模块边界

本项目延续集中式 `include/` + `src/` 布局，不套用通用文档中的 `engine/<module>/include/` 重组方案。

| 目标目录 | 职责与约束 |
|---|---|
| `include/tinyengine/` | 引擎头文件；内部头文件不因方便而暴露到此目录 |
| `src/` | 运行时实现及实现专用头文件，与公开模块职责对应 |
| `include/tinyengine/project_sdk/`、`src/project_sdk/` | 项目消费端封装和 C ABI，保持独立于完整引擎 |
| `editor/` | 编辑器 UI、文档状态、选择、Undo/Redo 等编辑器能力 |
| `programs/` | 资产、场景、打包、命令行和项目管理工具入口 |
| `cmake/` | 构建、SDK 安装导出、项目生成和产物清单逻辑 |
| `scripts/` | 仓库维护、构建及检查脚本 |
| `tests/` | C++ 测试程序、集成脚本和必要的固定输入 |
| `assets/` | 引擎自有素材、Shader、场景及其元数据 |
| `docs/guides/`、`docs/reference/` | 纳入 Git 的指南和参考文档 |
| `intermediate/` | 构建、依赖、生成文档等可重新生成的数据 |
| `saved/` | 日志、测试输出、恢复记录等本机运行数据 |

依赖要求：

- 基础类型、数学及 Core 不应反向依赖 Editor 或应用入口。
- 引擎运行时不依赖 ImGui 或编辑器文档状态。编辑器通过运行时接口工作。
- 独立工具复用引擎能力，入口层负责命令行解析、输出和退出码。
- 项目 DLL 通过 `tinyengine::project_sdk` 与宿主 C API 交互，不直接链接完整引擎、SDL 或 ImGui。
- 当前 Render 内已有渲染设备接口和 OpenGL 实现。新增后端需求出现前，不强制建立完整 RHI、多队列或跨 API 框架。
- 不为目录整齐把每个文件夹都变成独立 CMake target；存在真正依赖隔离、消费或测试需求时再拆分。

## 5. C++ 格式规范

### 5.1 目标格式

统一采用 Allman 大括号、4 空格缩进、禁止 Tab、120 列、指针和引用符号靠类型。根配置采用以下基线，具体工具版本在迁移交付时固定：

```yaml
BasedOnStyle: LLVM
Language: Cpp
Standard: c++20

IndentWidth: 4
TabWidth: 4
UseTab: Never
ColumnLimit: 120

BreakBeforeBraces: Allman
DerivePointerAlignment: false
PointerAlignment: Left
ReferenceAlignment: Left

SortIncludes: CaseSensitive
AllowShortFunctionsOnASingleLine: Empty
AllowShortIfStatementsOnASingleLine: Never
```

迁移必须更新根 `.clang-format`，对全部自有 C/C++ 源码运行同一版本的格式化工具，并更新 CI。上面的目标配置尚未在本次文档修订中写入根配置或执行格式化。

格式化与符号改名可分成便于审查的提交，但必须作为同一次迁移整体验收。交付后只有目标规则生效，不以旧配置或旧模块风格作为例外。第三方实现和生成产物不手工格式化；自有生成模板需确保输出符合规则。

### 5.2 手工规则

- 类、函数和控制流的大括号另起一行。
- `if`、`else`、`for`、`while` 等语句体必须使用大括号，即使只有一条语句；不能假定上面的格式化配置会自动补齐。
- UTF-8 编码，文本默认 LF。需要其他换行的外部工具文件单独配置。
- `if`、`switch`、`for`、`while` 与括号之间留空格；运算符间距交给格式化工具。
- 不把多个控制流、资源操作或错误分支压在同一行；不使用难读的嵌套三元表达式。
- 长字符串、外部格式等确实无法自然拆分的内容可以超过列宽；不通过破坏可读性机械满足列数。

### 5.3 类型与初始化

- 使用成员默认初始化，确保普通数据对象状态明确；服务对象允许通过显式 `initialize()` 完成可失败初始化。
- 使用 `nullptr`、`enum class` 和 `using`；C ABI 声明遵守第 2.3 节例外。
- 明确位宽的协议、磁盘格式和 ABI 使用固定宽度整数；内存长度优先使用 `std::size_t`，不把所有整数统一替换成 `u32`。
- 显式窄化前检查范围。使用 C++ 转换，低层 `reinterpret_cast` 应说明对齐、布局、有效期等依据。
- 浮点类型表达清楚，`float` 使用 `1.0F`，`double` 使用 `0.5`；全部自有源码统一字面量后缀风格。
- `auto` 用于初始化表达式已清楚揭示类型或类型冗长的场景；不隐藏重要的整数宽度、所有权或引用语义。

## 6. 头文件与依赖管理

- 头文件使用 `#pragma once`，必须能独立包含；直接包含所需依赖，不依赖偶然的传递包含。
- `.cpp` 优先包含配对头文件，其后组织项目、第三方和标准库依赖；各组内由格式化工具排序。
- 头文件禁止广泛的 `using namespace`。实现文件也优先使用有限范围的名字引入。
- 仅声明指针或引用时可前置声明；按值成员、继承和需要完整类型的操作必须包含定义。
- 使用 `std::unique_ptr<Impl>` 隐藏实现时，应在完整类型可见的位置定义需要完整类型的析构等操作。
- 平台头文件和大型第三方实现尽量留在 `.cpp` 或适配层。已经通过公开接口使用第三方类型的模块按实际需求处理，不伪称整个引擎完全无第三方公共依赖。
- 内部辅助函数优先放在 `.cpp` 的匿名命名空间，避免无意导出。
- C ABI 头文件不能包含 C++ 标准库或引擎 C++ 头文件，必须保持 C 编译验证。

## 7. 类型、API 与错误处理

### 7.1 类型与接口

- 一个类型承担清晰职责；优先组合，继承用于确有替换语义的接口。
- 小型数据按值传递；较大的只读数据通常使用 `const T&`；修改行为应从签名和文档可见。
- `T&` 表示有效对象，`T*` 可表示可空借用；裸指针默认不转移所有权。
- 单参数构造函数在无隐式转换需求时使用 `explicit`；重写使用 `override`。
- 资源所有者明确复制和移动策略。移动后对象必须能安全析构，不能保留重复释放同一资源的状态。
- 忽略返回结果会丢失重要失败信息时使用 `[[nodiscard]]`，不要对所有普通 Getter 机械添加。
- 服务的 `initialize()`、`shutdown()`、模块加载/卸载必须说明状态转换和失败清理。RAII 管理已经取得的资源；可失败的多阶段初始化通过明确结果表达。

### 7.2 统一失败表达

普通 C++ 操作统一使用小型项目级 `Result<T>` 表达可预期失败，错误包含稳定的 `ErrorCode` 和诊断上下文；没有成功载荷时使用 `Result<void>`。当前仓库尚无该设施，建立公共结果类型及迁移相关调用方属于本规范的实施内容。

结果契约：成功值和错误互斥；支持只可移动的载荷；提供 `hasValue()`、`value()`、`error()`；值/错误访问有明确前置条件；返回结果标记 `[[nodiscard]]`。错误文本服务于诊断，程序分支依据错误码，不解析字符串。结果必须携带本次操作的错误，不能依赖可能被后续调用覆盖的全局或对象 `getLastError()`。

| 场景 | 规则 |
|---|---|
| 加载、保存、初始化、编译、导入等可预期失败 | 返回 `Result<T>` / `Result<void>`，传播本次操作的错误 |
| 纯条件查询 | 使用 `bool`，例如 `isAlive()`；`false` 表示条件不成立，不附带隐含错误 |
| 正常可能不存在的值 | 使用 `std::optional<T>` 或明确约定的借用指针；确有 IO/解析等失败时使用结果类型 |
| 异步资源 | 状态查询与完成结果分开；检查 `getState()` / `isReady()`，完成结果包含失败原因；非空指针不代表已加载 |
| 项目/插件 C ABI | 使用对应模块的固定宽度结果码和明确输出参数；适配层转换 C++ 结果，不传 `Result<T>` 的布局 |
| JobSystem | 捕获非预期任务异常并在 `Job::wait()` 边界显式报告/重新抛出；业务失败通过任务结果传播 |
| 文件系统等库调用 | 将 `error_code` 或捕获到的可处理异常转换为统一错误，保证清理和诊断 |
| 内部不变量 | 可使用断言；外部输入仍须正常运行时校验 |

不使用异常作为每帧常规业务分支。异常可以用于库调用和非预期故障的边界处理，但不得穿越 C ABI、系统回调或线程入口。对这些边界做兜底捕获并转换为失败状态；不得把异常静默转成成功。析构和清理路径不抛异常，必要的最佳努力清理应保留可用的诊断或故障状态。不要机械把所有函数标记为 `noexcept`。

加载、导入、保存、打包等操作要明确失败后的对象和磁盘状态。需要事务语义时，先验证候选数据再替换有效状态；编译失败不能把旧产物标记为新构建成功。

### 7.3 日志与断言

- 引擎和编辑器统一使用 `Logger`，级别为 `Debug`、`Info`、`Warning`、`Error`；成员函数遵循 `debug()`、`info()`、`warning()`、`error()` 命名。
- CLI 的正常输出、错误输出和退出码属于工具契约，可以使用标准输出流；自有测试程序也可输出检查结果。
- 日志包含操作、相关路径或对象标识、失败原因；同一错误在最适合处理的位置报告，避免逐层重复。
- 热路径日志需要限频或调试开关；不输出密钥和访问令牌。
- 断言不能承担必须执行的函数调用，不能替代对文件、网络、脚本或 DLL 数据的边界检查。

## 8. 所有权、资源与生命周期

### 8.1 通用所有权

| 对象 | 约定 |
|---|---|
| 小型局部值、数学数据 | 优先自动存储期和按值语义 |
| 独占堆对象 | 优先 `std::unique_ptr` |
| 由缓存与调用方共同持有的资源 | 使用 `std::shared_ptr<Resource>` 表达实际共享生命周期 |
| 非拥有访问 | 引用或裸指针，说明被引用对象何时失效 |
| 实体 | 使用现有 `Entity` 代际句柄，访问前验证其所属 World 和存活状态 |
| 异步任务 | 明确捕获对象寿命、完成/失败处理和退出时的等待顺序 |
| DLL 对象和内存 | 由创建侧销毁，或使用同一套 ABI 分配/释放回调 |

`shared_ptr` 只管理对象寿命，不使对象内容自动线程安全。是否共享由持有关系决定；仅临时访问时使用借用，避免引用环。

`std::string_view`、`std::span`、容器元素引用、迭代器以及 ABI 字符串跨度都是借用。需要跨调用或跨任务保留时，应复制数据或提供明确的持有者寿命保证。

### 8.2 ECS 与资源状态

- `Entity` 包含索引和代际信息，不使用裸索引替代完整句柄。
- 不跨实体销毁、组件移除、World 重置长期保存组件裸指针；不能将当前存储实现的偶然稳定性当成公共契约。
- SDK 实体句柄还带 World 标识，不在不同 World 之间直接复用。
- `loadAsync()` 返回资源后必须检查状态；渲染和主循环不要随意阻塞等待磁盘任务。
- 删除或替换资产前检查引用关系；资源状态变化、缓存失效和 GPU 对象更新应有对应处理。

### 8.3 GPU 与退出顺序

- OpenGL 调用只能在持有正确 current context 的线程上进行；当前规范不假定引擎已有独立渲染线程。
- 后台任务可处理 IO 和 CPU 解码；GPU 创建、上传、更新和删除遵循后端已有线程约束。
- CPU 资源对象、GPU 缓存对象和资产 GUID 是不同层面的标识，不互相代替。
- 退出时先处理未完成任务和回调，再销毁其依赖对象；图形对象清理必须与 context 销毁顺序匹配。
- 当前不要求为 OpenGL 人为加入通用 Fence/延迟释放框架。未来后端若要求显式同步，应补充其资源完成和回收契约。

## 9. SDK、插件与跨 DLL 边界

项目模块与原生插件是两套已有 ABI，不能因为形式相似就互相套用结构和版本号。

1. 调用前检查 ABI 版本、`structSize` 和必要函数指针；读取可选尾部字段前确认结构长度覆盖该字段。
2. 结构演进优先在协议允许时追加字段，并保持旧消费者行为。破坏布局或语义时必须明确升级版本和拒绝不兼容组合。
3. 边界使用现有固定宽度值、借用字符串、透明句柄及函数表；不传 STL 容器、C++ 异常、虚对象或隐含 CRT 所有权的对象。
4. 分配与释放必须成对：宿主分配器产生的内存通过对应宿主释放回调销毁；模块对象通过模块提供的销毁函数销毁。
5. 卸载 DLL 前结束 Session、解除回调并销毁模块对象；卸载后不得再访问函数表或指向模块静态数据的指针。
6. SDK、宿主和项目模块遵守当前编译器、配置、SDK Build ID、项目 Build ID 和产物清单校验。不能把稳定 C ABI 理解成任意工具链组合均可加载。
7. 修改 SDK 头文件、模板、安装布局或构建身份计算时，必须验证源码树之外的 SDK 消费场景，包含中文和空格路径。

## 10. 注释与 Doxygen

### 10.1 注释语言和覆盖范围

自有源码注释以中文为主，必要时附英文术语。文件顶部说明职责和关键约束；无需机械重复完整相对路径、文件类型等工具已经提供的信息。

```cpp
/// @file
/// @brief 管理资源缓存条目及其共享生命周期。
/// @note 异步任务结束后才能销毁缓存依赖的服务。
```

公开类型和公共接口使用中文 Doxygen。接口说明必须覆盖调用者需要知道的语义：成功/失败、单位、可空性、所有权、有效期和线程要求；参数与返回值有额外语义时使用 `@param`、`@return` 明确记录。

私有辅助函数、普通字段、默认构造/析构和语义显然的访问器不强制堆叠模板化标签；简单公共接口可以使用准确的单句说明。重写可复用基类契约，只有额外约束或行为差异才补充说明。实现注释解释原因，不逐行翻译代码。

### 10.2 注释质量

- 说明成功条件、失败结果、单位、坐标空间、可空性、所有权和失效条件。
- 有线程、状态机或事务约束时必须明确记录。
- 避免“接口所需输入参数”“返回接口计算结果”等不提供契约信息的模板句。
- 不依据返回类型自动生成说明。例如比较运算符返回“是否相等”，并不表示“操作是否成功”。
- 修改语义时同步修改注释；现有不准确注释不能作为实现正确性的依据。
- 临时 TODO 应说明待解决问题和触发条件，不用空泛 TODO 代替已知失败处理。

迁移时同步调整 `Doxyfile` 的输入路径、公开接口范围和告警策略，使其检查本节要求，避免为了“每个私有参数都有标签”制造无信息注释。运行 `doxygen Doxyfile`，输出位于 `intermediate/documentation/`，验收要求接口文档无缺失或失真的契约描述、无文档构建告警。

## 11. 引擎数据、线程与坐标约定

### 11.1 数学与时间

保留已由数学实现确认的数学语义；下表接口名使用迁移后的命名：

| 项目 | 约定 |
|---|---|
| 矩阵存储 | 列主序，`at(row, column)` 对应 `data[column * 4 + row]` |
| 向量与组合 | 列向量语义；局部 TRS 为 `T * R * S`，作用时先缩放再旋转后平移 |
| 观察/透视投影 | `lookAt()` 与 `perspective()` 使用右手观察约定，相机观察方向对应观察空间 `-Z` |
| 基础投影深度 | 当前标准透视矩阵的 NDC Z 为 `[-1, 1]`；不能把窗口深度 `[0, 1]` 混为一谈 |
| 欧拉旋转与 FOV | 当前变换和透视 API 接受度；内部三角计算转换成弧度 |
| 帧时间 | 更新和固定步长使用秒；统计中的毫秒应显式换算 |

不要仅由这些数学函数推断所有资源的前向轴、导入单位、屏幕原点、UV 原点或特殊 Pass 的深度约定。相机、导入器、物理及渲染适配处必须记录转换。长度目前按项目场景单位处理；采用“1 单位 = 1 米”时，应明确配置并统一导入、物理和玩法尺度，不能声称全仓库已强制该比例。

固定更新由 `Engine::tick()` 统一协调；不得让子模块再独立推进同一段物理时间。回放或网络一致性需求需要明确随机种子、时间来源和更新顺序；当前不承诺跨平台逐位确定性。

### 11.2 线程与任务

- UI、World 修改和图形操作遵守所属模块线程约束，未声明线程安全的接口不能任意并发调用。
- 共享可变状态必须有锁、原子、消息交接或单线程归属；不能只靠 `shared_ptr` 或“线程安全”注释。
- 避免持锁等待其他作业、执行耗时 IO 或调用未知回调。
- 任务捕获 `this`、裸指针和引用前检查对象有效期；关闭和取消机制必须与实际支持的 API 一致，不假设所有作业都可取消。
- 不在音频回调等实时路径中进行阻塞等待、无界分配或高频日志输出。

### 11.3 资产、路径与序列化

- 持久化资产身份使用现有 GUID/元数据机制；重导入和改名不能随意生成新 GUID 或丢失引用。
- 资产路径按现有平台/资源接口处理；UTF-8 与 Windows 原生路径转换集中在边界，不能假定系统本地代码页等于 UTF-8。
- C++20 的 `char8_t` / `std::u8string` 与 `std::string` 不能视为可隐式互换。迁移时集中处理 `filesystem::path::u8string()` 和 UTF-8 字面量的类型变化，保留字节编码，并测试中文和空格路径。
- 共享配置不能写开发机绝对路径。SDK 和工具必须处理中文、空格和不同工作目录。
- 包内路径必须是规范化相对路径，拒绝绝对路径和目录穿越；校验字符串、数量、偏移和乘法溢出。
- 格式变化同步维护 Magic、版本、Reader、Writer 和迁移测试；不能直接把 C++ 对象内存当作稳定磁盘格式。
- 新字段设置兼容默认值，旧格式读取行为保持明确。更改既有字段语义时提供显式迁移。
- Shader、材质和 GPU 布局必须一起核对类型、对齐、绑定和缓存失效；不能只改 CPU 结构。
- 编辑器写操作同步处理脏标记、Undo/Redo、引用和恢复状态，不绕过已有文档/资产管理流程。

迁移前的格式与工作流资料见[资产与数据格式](asset_data_formats.md)、[原生插件 API](native_plugin_api.md)、[项目代码开发](../guides/project_code_development.md)。这些链接指向当前真实文件；迁移时分别改为 `asset_data_formats.md`、`native_plugin_api.md`、`../guides/project_code_development.md`，并更新内容中的接口和示例。

## 12. 性能与测试

### 12.1 性能

- 先定位热点，再评估分配、拷贝、锁竞争、缓存局部性、批处理和 GPU 同步。
- 复用现有分配器、任务系统和缓存；不为了“高性能”把所有对象改成裸指针。
- 当前 ECS 的存储方式不等同于 Archetype/SoA，不在规范中将其描述为已具备的数据布局。
- 优化报告应记录硬件、驱动、构建配置、数据规模及测量方式；保留正确性检查。
- 基准只针对需要长期观察的热点建立，不要求每个普通接口附带基准。

### 12.2 测试约定

测试通过 CTest 统一编排；当前小型自有测试程序可以承担检查，无需为形式统一引入额外框架。测试函数使用 `testBehavior()`，检查标签描述行为与预期；测试程序失败时返回非零退出码。不能只打印失败而让 CTest 判定通过，也不能仅依赖 Release 中可能被关闭的 `assert`。

- 功能变化测试可观察行为、边界输入和失败状态；Bug 修复优先加入能复现问题的回归。
- 不为纯格式、文案、改名等低风险操作编写镜像实现的单元测试，按影响检查引用、配置和构建即可。
- 新测试向 CMake/CTest 注册，并检查 `.gitignore` 是否允许跟踪。不能以“本机存在测试文件”代替可检出的测试。
- 测试输出放在专用 `saved/`、构建目录或临时目录中，不覆盖用户项目和真实资产。
- 尽量独立可重复；共享输出目录的测试不要盲目并行运行。
- 浮点和图像比较使用有依据的容差；GPU 测试记录驱动与环境需求，跳过原因必须可见。
- SDK/ABI 变化覆盖 C 头文件消费、版本/结构长度、错误码、卸载顺序和外部安装包消费。

常用本地入口：

```powershell
cmake --preset editor
cmake --build --preset editor-debug
ctest --preset editor-debug
```

需要发布验证或涉及配置差异时，使用对应的 `editor-release` 构建与测试预设。测试范围按改动选择，不能把未执行的完整测试声称为通过。

## 13. 构建与自动检查

- 通过 CMake target 配置依赖、include 和编译定义，正确区分 `PRIVATE`、`PUBLIC`、`INTERFACE`。
- 依赖版本和获取方式由现有 CMake 管理；新依赖应可重复获取并说明许可，不提交本机下载目录。
- 本机依赖路径使用未跟踪的 `CMakeUserPresets.json` 或配置参数，不写入共享工程。
- 自有目标使用 MSVC `/W4 /permissive- /WX`，GCC/Clang 使用 `-Wall -Wextra -Wpedantic -Werror`；统一迁移解决自有代码告警，不全局关闭告警掩盖问题。需要平台局部例外时限定具体检查和范围，并记录技术原因。
- 第三方包装编译单元可采用局部告警例外，不把例外扩散到自有代码。
- 不同时启动多个写入同一 Visual Studio Build Tree 的构建；Debug/Release 的宿主、SDK、项目产物不得混用。

自动化是统一迁移的交付内容：

| 检查 | 交付要求 |
|---|---|
| clang-format | 固定工具版本，检查全部自有 `.h`、`.cpp`、`.c`、`.tpp` 等适用文件；任何失败使 CI 失败 |
| clang-tidy 命名检查 | 加入 `.clang-tidy`，检查函数、成员、常量、类型和命名空间；C ABI、第三方接口按其明确规则处理 |
| 文本与文件命名 | 加入 `.editorconfig`，同步 `.gitattributes`，检查 UTF-8、LF、文件名及大小写冲突；命名检查不能只覆盖 C++ 符号 |
| 构建 | Windows 上验证 core/editor、Debug/Release 及 SDK 消费端；只构建 core 不能代替编辑器和 SDK 检查 |
| CTest | CI 执行可运行的 CPU/集成测试；GPU/UI 测试在具备环境的运行器执行并报告，不将跳过算作通过 |
| 内容与打包 | 通过资产/场景校验、Cook 和打包，实际启动生成的项目与游戏包 |
| Doxygen | 验证公共契约文档，构建无告警 |
| 内存和线程检查 | 选择实际支持的 Sanitizer/诊断工具并记录运行结果；不宣称 Windows 主构建覆盖了所有平台和线程检查 |

工具配置必须进入 Git；迁移后全部自有源码、测试和脚本在新路径下可从干净检出构建。不能靠本机旧头文件、旧 DLL、未跟踪脚本或旧缓存使检查通过。

## 14. Git 与审查

- 一个变更聚焦一个主题，格式化、批量改名和行为修改尽量分开。
- 提交信息清楚描述行为和原因；`fix(resource): ...`、`docs: ...` 等前缀可选，不作为必须执行的发布协议。
- 不提交构建产物、依赖下载、IDE 缓存、本机配置、敏感信息和无分发权限的素材。
- `docs/` 下仅迁移后的 `guides/` 和 `reference/` 纳入 Git；这与原 `Guides/`、`Reference/` 的管理范围一致。架构草稿、计划和报告保留本地。仓库根 `README.md` 仍是项目入口。
- 新规范和必要的长期开发契约放入受跟踪文档目录；不能依赖未跟踪草稿作为其他开发者必须读取的唯一依据。
- 审查重点是正确性、所有权、线程、ABI/格式兼容、失败路径和验证证据。
- 修改公共接口、SDK、序列化或安装布局时说明兼容性影响、迁移方式及验证范围。

## 15. 一次性迁移与验收

### 15.1 执行顺序

一次性迁移指整个仓库交付时使用同一套规则。执行中可以按依赖分步骤、分提交验证，但不能把不合规的旧模块留作长期例外。

1. 建立所有自有文件、符号、公开头路径、SDK 导出及引用映射；记录迁移前的构建和功能验证结果。
2. 统一 C++20 构建和工具版本，设置根格式、命名、编码及 CI 检查，处理 UTF-8 等语言变化。
3. 批量迁移文件、目录、命名空间、函数、常量、类型缩写、C ABI 和 CMake 导出名称；同时更新全部调用、配置、生成模板和文档。符号改名使用编译语义或经过核对的映射，不对任意字符串盲目替换。
4. 统一可失败操作的结果契约，完善所有权和边界注释，移除只复述代码的模板注释。错误传播变更单独审查行为。
5. 按目标风格格式化全部自有源码，检查无遗漏旧 include、旧导出符号和旧命名；例外只来自第 3.2 节的明确范围。
6. 在新目录重新配置，从干净检出执行构建、测试、SDK 安装消费、内容校验、打包与实际启动。依赖、缓存和生成产物重新生成，不用旧产物掩盖遗漏。
7. 更新版本、迁移说明和相关示例，一次性发布匹配的宿主、SDK、模板和项目产物。名称整理不应改变资源 GUID；需要升级数据格式时验证转换结果。

统一风格不要求另外设计完整 RHI、Archetype ECS 或多线程渲染架构。这些是需要独立需求和性能证据的架构选择，不能仅由命名统一推导出来。

## 附录 A：统一目标与修改理由

| 当前实现或上一版保留项 | 统一目标 | 设计理由 |
|---|---|---|
| C++17 | C++20 | 为借用区间、模板约束和格式化提供语言/库基础，同时统一 SDK 消费标准 |
| `LoadAsync()`、`IsAlive()` | `loadAsync()`、`isAlive()` | 类型使用大驼峰、操作使用小驼峰，角色区分直观 |
| `InvalidEntity`、`Pi`、`MaxLights` | `kInvalidEntity`、`kPi`、`kMaxLights` | 编译期常量易于辨认；运行期 const 变量保留普通变量规则 |
| `tinyengine::project_sdk` | `tinyengine::project_sdk` | 统一产品身份、命名空间与包含路径 |
| `PluginAPI`、`SDKPaths` | `PluginApi`、`SdkPaths` | 缩写按单词处理，避免不同缩写各自发明拼写规则 |
| `u8`、`u32` 等纯缩写别名 | `std::uint8_t`、`std::uint32_t` 等 | 标准类型直接表达位宽；别名用于领域语义 |
| 大写目录、`.hpp`、中文文档文件名 | 小写 `snake_case`、`.h`、英文文档文件名 | 代码、构建、安装、文档遵循统一路径规则 |
| Microsoft / 140 列 | LLVM / Allman / 4 空格 / 120 列 / 左侧指针与引用 | 落实已确定的格式要求 |
| `TinyProjectAPI`、`TinyProject_GetAPI` 等 | `TinyEngineProjectApi`、`tinyEngineProjectGetApi` 等 | 自有 C 接口同样有一致的前缀、缩写和字段规则 |
| 多种普通操作失败约定、可覆盖的最后错误 | `Result<T>` / `Result<void>`，明确错误码 | 值和失败绑定在同一次调用，便于调用方正确处理 |
| 每个私有函数、参数均堆叠注释 | 公共契约完整、复杂约束明确、简单实现少注释 | 注释承载代码无法表达的信息，减少失真和噪声 |
| CI 只覆盖部分格式、core 打包 | 格式/命名/构建/CTest/SDK/内容/打包验收 | 自动阻止回到混合风格，验证全部实际交付入口 |
| 逐步迁移与旧路径豁免 | 全仓库一次性交付 | 全部自有模块使用同一套目标规则 |

集中式 `include/` + `src/`、共享资源缓存、代际实体、OpenGL 后端和 C ABI 边界继续采用，因为它们分别对应职责组织、共享所有权、失效检测、实际后端和跨 DLL 隔离需求。

本版依据当前构建、格式、Types/Math/Logger、ECS/Resource/JobSystem、两套 C ABI、SDK 导出、Runtime 和测试代码审阅。这里描述的旧名称仅用于定位迁移对象，不是目标规范的例外。
