# TinyEngine 源码阅读与注释规范

本文说明源码中的中文注释承担什么职责，以及个人开发者阅读项目时建议采用的顺序。注释用于解释边界、所有权、线程、数据约定和设计原因，不替代可读的命名与测试。

## 注释层级

每个项目自有的 `.h`、`.hpp` 和 `.cpp` 文件顶部都有四项说明：相对路径、文件职责、所属模块的重要约定以及文件类型。新增源码文件时应同时补齐这四项。

头文件中的每一个函数接口都必须使用 Doxygen 中文注释：

- 每个函数、成员函数、构造函数、析构函数、运算符、模板接口和回调函数都有 `@brief`；
- 每个具名参数都有 `@param`，说明单位、坐标空间、所有权或允许为空等约束；
- 每个非 `void` 接口都有 `@return`，布尔接口明确成功条件，指针和引用明确失效规则；
- 重载和重写接口也分别记录，不能只依赖另一个重载或父类的说明。

公开类型或 API 在下列情况还需要补充设计约束：

- 对象拥有或借用另一个对象，且有效期不能从类型签名直接判断；
- API 只能由主线程、渲染线程、音频回调或工作线程调用；
- 状态机、实体句柄、资源句柄或网络序列号存在失效规则；
- 输入输出有坐标系、矩阵顺序、单位、数量上限或安全边界；
- 一次操作具有事务语义，例如场景加载、资产导入、撤销和打包。

实现文件只注释不容易由代码本身表达的原因。典型内容包括固定时间步的目的、异步任务如何避免重复加载、Render Graph 为什么计算资源生存期、网络解码为何先写临时对象，以及编辑器输入之间的优先级。不要为简单赋值、循环或函数名已经说明的行为逐行翻译。

## 推荐阅读顺序

1. `include/MiniEngine/Types.hpp` 与 `Math/Math.hpp`：了解实体句柄、坐标和矩阵基础。
2. `ECS/ECS.hpp`、`ECS/Components.hpp`：理解 World、实体代际号和组件存储。
3. `Task/JobSystem.hpp`、`Resource/Resource.hpp`、`ResourceManager.hpp`：理解并发和资源状态机。
4. `Render/Renderer.hpp`、`RenderGraph.hpp`、`SdlGlRenderDevice.hpp`：理解一帧如何从 World 到 GPU。
5. `Physics/PhysicsWorld.hpp`、`Animation/SkeletalAnimation.hpp`、`Audio/AudioEngine.hpp`：阅读运行时功能模块。
6. `Project/Project.hpp` 与 `Runtime/Engine.hpp`：理解项目、场景以及整个生命周期的组装。
7. `editor/EditorApp.hpp` 和 `EditorApp.cpp`：最后阅读编辑器如何调用上述能力。

## 维护规则

- 修改接口语义时，同一提交更新对应注释；已经失真的注释比没有注释更危险。
- 注释说明“为什么、约束是什么、谁拥有”，代码说明“具体怎么执行”。
- 中文术语首次出现时可保留通用英文名，例如“渲染图（Render Graph）”，便于检索资料。
- 测试钩子和仅用于自动化的源码标记必须明确写出用途，产品逻辑不能反向依赖测试代码。
- 第三方源码不做批量注释；本项目只在隔离第三方实现的包装编译单元说明边界。
- 提交前运行 `doxygen Doxyfile`；`build/doxygen-warnings.txt` 必须为空，生成文档位于 `build/doxygen/html/index.html`。

## 本轮覆盖范围

本轮已为 `include/`、`src/`、`editor/`、`tools/` 和 `tests/` 中的项目自有 C/C++ 文件补充中文文件说明，并为头文件中 Doxygen 可解析的全部函数接口补齐 `@brief`、`@param` 和 `@return`。Engine、ECS、作业系统、资源、渲染、物理、动画、网络、Assimp 导入、Runtime UI、项目/Prefab、插件和编辑器还保留了关键设计路径说明。注释变更不修改运行逻辑。
